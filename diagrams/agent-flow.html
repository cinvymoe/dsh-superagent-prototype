提示不是启动时灌进去的

一个 Session 从被建出来到交回最后一句话，中间只经过一件事：每来一次模型请求，宿主把当前该给它看的东西重新拼一遍，交给模型。这张图画的是那条流程，以及拼装发生在哪三个时刻——建立时一次、每次请求一次、每次回报之后一次。

读这张图的方式

三段，一个循环

① 是进门：Trigger 被主 Session 读一次，落成 Decision 与 Ticket。② 是这一单的一生：Session 建好之后就在「拼提示 → 请求 → 写回」之间转圈，转多少圈由这一单要做多少事决定。③ 是离场：report 收工，PR 合并后按策略落地。

  • coral 的两处不是流程步骤，而是提示被写进上下文的位置。
  • 回到「拼提示」的那条线就是「下一轮请求」——它每次都重来，不是缓存。

注入的到底是哪几样

三样东西，一个入口

  • 能力：tools 按角色决定（主 Session 有 orchestrator_route，aligner 才有 orchestrator_align），skills 由设置与团队决定。
  • 人格与规则：prompts/shared.md + 角色段 + 团队三段（Communication / Ticket scope / Delivery），改「设置 → 提示词」立即影响下一次请求。
  • 这一单的活：mandate 追加在末尾，只有 worker 与 aligner 有。

为什么每次都重拼

改了就要能立刻生效

提示词版本、策略规则、环境变量、mandate 都会在执行中途变化。若启动时固化一次，这些改动要等这一单结束才生效。代价是每次请求多一次拼装——实测一个角色的系统提示在 27K–32K 字符之间。

  • 首行的 [dsh-superagent prompt revision N] 是给模型与排查用的版本锚点。
