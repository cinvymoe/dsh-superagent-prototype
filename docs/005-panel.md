# 005 Panel

Open **Superagent** in the DeepSeek Harness Web sidebar to supervise the agent. The panel prioritizes work that needs a person, then system health and history. This document builds on [000 Philosophy](000-philosophy.md) through [004 Prompts](004-prompts.md).

## Three questions

Opening the panel answers three questions, in this order:

1. Does anything need me now?
2. Is the system healthy and doing the right things?
3. What is the history of one piece of work, from Trigger through Eval to Ticket?

### Permalinks

The address bar names the page the panel is showing, and each page has an address a person can copy or open in a new tab. The parameters are `panel=dsh-superagent` with `page`, plus `id` for an open record, `filter` for a list, `create` or `edit` for a requirement form, `group`, `source` and `version` for Settings, `trigger` for a selected Trigger, `window` for the Eval window, and `project` for the current project. The panel replaces the address bar's search on navigation instead of pushing an entry, so browser history stays out of the panel's route stack and the panel's own Back button keeps returning through its pages. Leaving the panel removes those parameters again, so a plain refresh on another page of the shell behaves as it did before.

Opening a URL that carries `panel=dsh-superagent` selects **Superagent** in the sidebar and opens the named page, record, filter and project. A URL without the marker is ignored and the session's remembered route is used, as before; a marker naming a page the panel does not have falls back to that remembered route and then Overview. The link at the right of the page header opens the current page in a new tab: its `href` is the same permalink the address bar holds plus `standalone=1`, it never carries a launch token, and there is no separate copy or share control.

`standalone=1` makes that tab the panel on its own rather than a page framed by the host: the document gets a `data-dt-standalone` marker, the panel's stylesheet drops the shell's sidebar column and hides the sidebar, and the browser title names **Superagent** instead of the host's product title (restored when the panel is left). An ordinary permalink keeps the shell's columns, so a URL copied out of the address bar still opens inside dsh.

### Creating a requirement

**New requirement** above the requirement list opens a dialog over it; the separate New requirement page is gone. The dialog names the target project and its repository chain and has one description field: its first non-empty line becomes the title, with whitespace collapsed and shortened to 200 characters, while the whole description is stored as the body. **Choose images** attaches up to four PNG, JPEG, WebP or GIF files of at most 5 MiB each; each shows a thumbnail and its file name and can be removed before submitting. Pasting a clipboard image or dropping image files on the box attaches them the same way, without inserting any file-name text into the description. Submit stays disabled while the description is blank. Opened from a discussion's result panel, the dialog fills the description once with that discussion's text, which stays fully editable, and submits the discussion id with the requirement. A refused create keeps the dialog open with the description and the chosen images, and nothing is cleared before the request succeeds.

### Projects

Each local project owns one GitHub repository chain and has a project name, an intake repository, a code repository, an optional bot, an optional worktree root, an optional prepare command and optional additional blocked commands. **Project name** labels the project in the project bar and on its requirements. **Intake repository** is the `owner/name` repository whose Issues the project receives. **Code repository** is the `owner/name` repository that executes the project's requirements, and it is their only execution target; it is the project chain's code repository. The project's chain is stored in the GitHub Source's repository chains under the project's id, so creating or editing a project only adds or changes that project's chain and leaves every other project's chain untouched. An intake repository belongs to one chain only: creating or editing a project with an intake repository another project or chain already receives from is refused as a conflict, naming the project or chain that holds it, and neither the project nor the chains change. **Bot** is the GitHub CLI wrapper signed in as the account this project's requirements act as; it is written only to that chain's own CLI field, and empty keeps the chain on the GitHub Source's default CLI. Saving validates the CLI and its account against the chain's repositories, and an unusable or signed-out CLI is refused with its localized reason while the page keeps the typed values. The panel derives each project's bot account from its chain on every read, so the requirement pages and the **More** menu show the account of the current project and switch it with the project. **Worktree root** is an optional absolute directory root for the project's Tickets; empty keeps the Execution ticket directory root. **Prepare command** is an optional command that replaces the Execution prepare command for this project's Tickets; empty keeps the Execution one. **Additional blocked commands** are optional command names that fail only in this project's Executor Session, on top of the Execution blocked list, which still applies to every Ticket: the effective list is their union without duplicates, `gh`, `git` and `lark-cli` can never be blocked, and empty adds none. The requirement page heads also show the project's worktree root when it sets one, whether it sets its own prepare command, and which commands it blocks in addition.

When dsh-superagent starts, a project stored by an older version with only an execution repository is bound to the existing chain whose code repository is that repository, without changing the chain configuration; a project with no matching chain keeps executing in its original repository. The project bar above the page tabs selects the current project; the requirements, their page head and a new requirement all follow it. **New project** on the bar opens the creation page, and the requirement list page head's project link opens the current project's own page under **Settings → Projects**, which edits the same fields already filled in and the settings that project overrides. A project stored without a chain does not offer the bot field, because it has no chain row to write it to. Cancel or Back on either page writes nothing. Saving the creation page reloads the projects, makes the saved project current and opens its own page under Settings → Projects; saving that page stays on it and reloads the project bar, and editing one project changes only that project's chain and leaves every other project's two repositories as they were. A refused save shows the localized reason and keeps the page and the typed values.

### Project settings

The **Projects** group under Settings lists every project and gives each one its own page, so a project is edited on its own page rather than on the requirement list. That page carries the project record fields above, and below them the two settings the project may override: **Pause this project** stops its Tickets, and **Executor model** gives its worker Sessions a model of their own; empty means the project inherits the Execution settings. Saving the record and saving the override are separate: each writes on its own and keeps its own history, so pausing a project never rewrites its repositories and the other way around. **Use the global value** removes the override instead of copying today's global value, which restores inheritance. The project's worktree root, prepare command and extra blocked commands stay on its record and still outrank the Execution settings, while rules and evaluation remain global and cannot be overridden.

A configured worktree root must already exist and accept writes; otherwise the Ticket fails to launch instead of falling back to the Execution ticket directory root.

### Discussions

The figure [`diagrams/discussion-to-requirement.html`](../diagrams/discussion-to-requirement.html) traces one discussion into one requirement, field by field. The figure [`diagrams/discussion-routing.html`](../diagrams/discussion-routing.html) draws the route around it: the Router's `discuss` decision, the read-only Answerer that answers it, and the hand-off that starts the one alignment Ticket.

Every discussion belongs to one local project and lives on its own Thread, apart from the project's requirements. The **Discussions** page lists the current project's discussions newest first; each row shows whether it is Open or Closed, whether it already created a requirement, and when it was created. **New discussion** above the list opens a dialog for the text and images: its first non-empty line becomes the title and the whole text is stored, with the same title rules as a requirement's description; a message with images and no text is accepted and takes its title from the first image's file name.

A discussion detail shows the body once with its images, then its message timeline newest first with the follow-up box above the list, each message carrying its own images and the answer below it. When the Answerer needs a decision from the person to conclude, it puts one to three questions on a card above that box: each question offers its proposed answers as buttons and a field for another one, and **Send answers** posts the answers into the discussion as one message, which the Answerer answers next. Asking creates no Trigger, Ticket or Eval of its own, and only one card is open at a time, so a second ask waits for the first card to be answered. The result panel sits in the right column beside it, showing the latest conclusion, the answer state and the actions it allows. Its messages are ordinary human Triggers on the discussion's Thread, and the discussion's own read-only Answerer Session answers each: no message becomes a Ticket, and nothing here aligns, dispatches slices or creates a requirement. An answer still in progress shows its state; a failed one shows the failure and **Retry**, which asks the same Session again, and a message written before answers were recorded still shows its text from the Thread. **Close discussion** sets the discussion to Closed and leaves its Thread and messages readable. **Delete discussion**, shown only while the discussion is about no requirement, asks for confirmation naming its title; confirming archives its Answerer Session, removes the record, its Thread with the Triggers that belong only to it, its images and its state-directory workspace, then lands on the list without that row. A discussion that is about a requirement is refused and keeps its record and messages, because that requirement still names it as its source. A discussion is about at most one requirement: a person makes the requirement from it, or the Router opens it about an existing requirement whose work is not decided yet. A requirement made from a discussion shows that source discussion in its detail and links back to it.

**Send to issue** in the result panel turns a discussion into a requirement: it opens the requirement dialog with the discussion's text filled in once, still editable, and the submitted requirement records the discussion as its source while the discussion records that one requirement. The link is shown in both directions, so the requirement detail shows its source discussion and opens it again. A discussion creates at most one requirement, and once it has one, **Open requirement** replaces Send to issue. A discussion the Router decided to talk through arrives already linked to its requirement, so it goes straight to Open requirement.

**Give to alignment** hands the discussion's conclusion to the alignment worker. It is available once the discussion is about a requirement and has an answered message: it starts that requirement's single alignment Ticket with the latest answer as the routing note, and the result panel then shows that Ticket, so the alignment worker proposes the slices from what the person already read here instead of asking again. Handing over again returns the same Ticket rather than starting a second, the discussion stays open for later messages, and a requirement whose alignment is already confirmed refuses the hand-off.

### Requirement execution mode

A requirement executes its slices in one of two modes: `native`, where each worker implements its approved slice directly, or `feature-exec`, where each worker runs it through the execution stage. While the alignment proposal waits for confirmation, the detail's alignment card carries the switch, **Run the execution stage with feature-exec** (执行阶段使用 feature-exec). It is off by default, which is `native`; turning it on selects `feature-exec`. There is no global or per-project default, so each requirement chooses its own mode in its alignment card.

The switch saves immediately through `POST local/issues/:id/execution`, and a reload shows the stored mode. The requirement list row shows the mode as a tag, **Native** while the requirement made no choice.

Once the requirement has dispatched slice Tickets, its mode is fixed: the alignment card shows the stored mode as a read-only tag with the hint **Tickets are already dispatched, so the mode is fixed.** (已派发工单，执行方式固定。), and a further change is refused with `executionLocked`. A person therefore chooses the mode before confirming the alignment.

### Requirement states

The figure [`diagrams/requirement-lifecycle.html`](../diagrams/requirement-lifecycle.html) draws those states together with the alignment rounds and the dispatch step.

A requirement's state label is **Open** while work remains and **Closed** after a person closes it. Once the requirement's alignment is confirmed and every slice Ticket of that alignment has ended, an open requirement shows **Pending close** (待关闭) instead of Open, and its alignment tag stays **Confirmed** (已确认); a closed requirement shows only **Closed**. Both ways a slice Ticket ends count — an Executor's result report and a person's stop — so Pending close means execution has stopped and only closing is left, not that every slice succeeded. A requirement with no alignment, with a proposal awaiting review or one sent back, stays Open, and a confirmed alignment with no slices or with a slice whose Ticket is missing never shows Pending close. The label is derived when the panel reads the requirement, not stored: if a Ticket resumes, the label returns to Open.

### Requirement images

**Choose images** in the requirement dialog attaches up to four files to one requirement. The limits are PNG, JPEG, WebP or GIF only, at most 5 MiB per image and at most 4 images; the form states them below the button.

- **Choose images**, a clipboard paste or dropped image files all use the same intake; a pasted image shows its thumbnail and file name and never inserts its name into the description.
- An image over 5 MiB is downsampled to a JPEG whose longest edge is 2560 at quality 0.9 before attaching instead of being refused; a result still over 5 MiB is refused with the size reason.
- The client refuses an unsupported type or a selection that would exceed four images, shows the reason and adds nothing, so no request is made. The already chosen images stay. A pasted non-image adds nothing.
- Pasting the same file twice keeps one entry, and an unnamed clipboard screenshot is attached as `pasted-<timestamp>.png`.
- Submitting sends the description and the images in one create request, so the requirement exists with all of them or with none.
- When the host refuses the create, the description and the chosen images stay on the page and the localized error appears; nothing is cleared before the request succeeds.
- The detail shows the images in submission order, each with its file name and byte size. The list row adds the image count.

Images are read through the same-origin management API (`GET /orchestrator/api/local/issues/<id>/images/<imageId>` with the `x-orchestrator-request` header) and rendered from an object URL, so there is no unauthenticated image URL and no `<img src>` request without that header.

### Discussion images

The new-discussion dialog and a discussion's follow-up box accept images by paste, drop or **Choose images**, under the same PNG, JPEG, WebP or GIF, 5 MiB and four-image limits as a requirement's. A message may be images alone; a new discussion then takes its title from the first image's file name.

- An image belongs to the message that submitted it: the new discussion's images show beside its body, and a follow-up's images show only in that message's timeline row, never on another.
- The Thread Trigger names every image's absolute path in an `Images:` block, and the read-only Answerer receives the same block, so it can read what the person attached.
- The images are stored under `<stateDir>/local-images/discussions/<discussion id>/`; deleting a discussion removes that directory with the record, its Thread and its workspace. A discussion that created a requirement is still refused, and its images stay.
- A refused image (type, size or count) returns the same localized `issueImage*` wording as a requirement's, and neither the record nor any bytes are written.
- Images are read through `GET /orchestrator/api/local/discussions/<id>/images/<imageId>` with the `x-orchestrator-request` header and shown from an object URL, so no discussion image has an unauthenticated URL.

### Requirement follow-up images

The follow-up box above a requirement's message timeline and each waiting Ticket's answer box accept images by paste, drop or **Choose images**, under the same PNG, JPEG, WebP or GIF, 5 MiB and four-image limits as a requirement's. Both post a human comment through `POST local/issues/<id>/comments`, and a message may be images alone.

- An image belongs to the message that submitted it: only that message's timeline row shows it, never the requirement card or another message.
- The Thread Trigger names every image's absolute path in an `Images:` block, so a worker that receives the message through the Engine can read it with `read_image`; the panel hides that block and shows the thumbnails instead.
- The images are stored in the requirement's own `<stateDir>/local-images/<issue id>/`, and each message's entry names the Trigger it became. The requirement card's gallery and the list row's image count still cover only the images the requirement was submitted with.
- A refused image (type, size or count) returns the same localized `issueImage*` wording as a requirement's, and neither the record nor any bytes are written; a follow-up with neither text nor an image is refused with its own wording.
- Images are read through `GET /orchestrator/api/local/issues/<id>/images/<imageId>` with the `x-orchestrator-request` header and shown from an object URL, so no follow-up image has an unauthenticated URL.

### Reading individual records

A dropped message links to its Ticket, or to its Thread when it has no Ticket. The Source page explains whether its conversation disappeared or the Source stopped listening to it.

A human follow-up still owned by an Executor is marked **Delivered to Ticket**, without an Eval. The Thread also shows hand-back reasons and context-only Subscriptions. **Evaluate again** can send that follow-up to Eval, or retry a Trigger with no effective judgement: one filtered by its Source, an unavailable Eval, or a delivered message with neither a non-stop Decision nor an Executor acknowledgement.

Ticket details show the originating Trigger, Decision and reason, scope and Policy version. Assignments and secondary details are folded below the immediate actions. **Retry** is available for failed Input delivery or a Ticket waiting for a person after a blocked or failed Report. Ended Tickets show outcomes such as **Pull request merged** or **Stopped by a person**.

## Settings groups

- **Sources:** one card per Source with its switch, fields and verified account facts. The local source backs the Discussions and Requirements pages; its projects, discussions, issues and replies stay in this installation, and each project owns a GitHub repository chain (intake repository → code repository) stored in the GitHub Source's repository chains, whose code repository is the execution target for its requirements; its `worktreeRoot` (when set; empty keeps the Execution root) is the directory root for their Tickets, its `prepare` command (when set; empty keeps the Execution one) replaces the Execution prepare command, and its extra blocked commands (empty adds none) apply only to its own Tickets on top of the Execution list. Each GitHub chain row may name its own CLI; a blank one uses the card's default CLI, and **The account of each chain** lists the account setup resolved for every chain. Deleting or renaming a chain a project uses is refused with that project named, so a project cannot silently lose its intake repository; change a project's own chain from its edit form, and two chains cannot receive Issues from the same repo either, so an edit that would create such a duplicate is refused with the chain that already holds it. GitHub also offers receive-all switches for new Issues, pull requests, comments and default-branch CI. Polling and read limits are under Advanced.
- **Eval:** the Policy version and rules, followed by **On each Source** and the Eval settings. **Delivery** sits between the version line and the rules: one switch, **Land a merge on this machine** (`policy.delivery.land`), which is off by default. On, a merged pull request of a chain's repository pulls and rebuilds the running checkout and lets the service unit restart the process once no Ticket runs; off, a merge stays at the remote until a person refreshes and restarts, as before. The switch changes delivery, not who may originate work, so it makes no new Policy version. Each Source tab contains its allowed list, membership sync, admission table and bot list. Sync runs at startup and on **Sync now**. The admission table distinguishes receiving scope, sender membership and whether the message addresses the agent. Eval settings select the accept mode, timeout and assessment model.
- **Execution:** Executor model, concurrent Tickets, the Ticket directory root (`executor.directory`; empty uses `<stateDir>/work`), prepare command (empty starts a Ticket in an empty directory) and blocked commands (empty blocks none). A local project's `worktreeRoot` takes precedence over the Ticket directory root; an explicitly set root must already exist and be writable, or its Tickets fail to launch instead of falling back. The prepare command runs in the selected root. A local project's own `prepare` command replaces it for that project's Tickets. The blocked list applies to every Ticket, and a local project's additional blocked commands add to it without duplicates and fail only in that project's Executor Session, while `gh`, `git` and `lark-cli` can never be blocked. Clicking an available variable inserts it into the prepare command. **Per project** below those blocks lists every local project with the only two settings it may override: a switch that pauses that project's own launches and an executor model for the worker Sessions it starts. A project with no row entry keeps the global values, so a save only records what differs, and **Use the global value** drops its entry again rather than copying today's global value into it. Saving this block is panel-only and carries its own history. Where a project runs, how it prepares and what it blocks are its own project fields, not overrides here, and authorization stays global: one Policy judges every project. The execution mode is not a setting here: there is no global or per-project default, and each requirement chooses its mode in its alignment card before dispatch.
- **Agents:** the main Session, the worker and the answerer, each with an optional model override and a switch per plugin it may enable. A plugin is a capability group: enabling one brings every tool it declares, and a role's read-only required tools stay on regardless. The built-in groups are `image`, `web`, `skills`, `todo`, `subagents` and the four runtime-mounted capabilities `ask-user`, `present`, `web-fetch` and `fork-subagent`, which the host mounts into a Session only while their switch is on, so a disabled one adds neither a tool nor a prompt section; those rows carry a **运行期挂载** tag, and enabling one also enables the plugins its `requires` names; the main Session enables `image` and the seeded `billion-context` definition by default (the six compression tools arrive only when the host provides them, and the definition is a stored plugin this panel can edit or delete, offered on the main role only), and a worker enables `image`, `web`, `skills`, `todo` and `subagents`. Each row lists the plugin's tools, marks a stored plugin **自定义**, marks a disabled switch **已停用**, and marks tools this host does not register **宿主未提供** with their names, which never enter the allow list. Subagents have no separate configuration and inherit the worker's plugins. **Custom plugins** above the role cards is the shared catalog: **Add plugin** groups the host's MCP servers (`mcp__<server>__…` tools), every tool-name prefix at least two tools share and the remaining tools, and a suggestion fills the name and its whole tool set in one click; the dialog takes a name, a tool set (extra names may be typed, including tools this host does not register) and the roles the plugin applies to. An added plugin is switchable on each applicable role before the save, and **Delete** removes it from the catalog and from every role's enabled list, asking first when a role has it enabled. A stored plugin may declare a tool this host does not register: the save keeps it and the row lists it under **宿主未提供**, while Sessions drop it from their allow list. A blank model shows the value that role inherits and **Restore inheritance** clears an override again: the main Session inherits the assessor model, the answerer the worker's effective model (the worker's own override first, then the executor model in Execution settings), and the worker the executor model in Execution settings. A refused save keeps the edits and shows the localized reason, such as a plugin that does not apply to that role. The worker card shows its running load and links to the Execution settings for concurrency, which is not edited here. Saving is panel-only, and the history lists each Agent save with its role, model, plugin enable/disable and stored plugin add/remove changes.
- **Prompts:** **Edit** changes team sections, built-in parts and skills. **Full prompt** shows the assembled text and compares it with saved text or defaults. **History** lists versions. Edited built-in parts are marked changed and can be reset; templates list their required placeholders.

  An upgrade that changes an overridden default marks it **Default updated** (默认内容已更新). The panel compares the old and new defaults above the team's text. If the old default was not recorded, it compares the team's text with the new default instead. Choose **Keep my text** or **Use the new default**. Overrides for removed parts are listed below the tab bar and dropped on the next save.
- **Deployment:** startup problems with **Check again**, the state directory and machine limits. Saved limits apply without restart. **Running checkout**, the checkout the running plugin loads, shows its path, branch, commit and the commit's time, its work tree, and the matched chain repository, with the reasons when it cannot take a merge; once the disk moved past the running instance it also shows **Takes effect after a restart**. **Pull and build**, behind a confirmation, fetches `main` from that repository and rebuilds the checkout, and it never restarts the service, so the new build takes effect after a restart. The DeepSeek Harness Plugin Manager exposes the same page.

## Search

The header search finds Triggers by text, id, Feishu message id or a stored link, such as a GitHub comment URL. A Feishu link missing from the original message becomes searchable only after the host reads it during the current process lifetime.

Search also finds Threads by references such as `#12` or a GitHub URL, and Tickets by title or a matching Thread.

## Principles

1. **Focus on what matters.** Every element answers one of the three questions, or it is removed. A number appears only when it changes what the supervisor does.
2. **Precise definitions.** Categories have checkable definitions, are mutually exclusive and cover every case, as the Ticket stages do. A label says whom a row waits for and what it needs, not an internal status code.
3. **One place per concept.** Source state belongs in Source; Threads and Triggers in Trigger; Decisions in Eval; Tickets in Execution. Settings are grouped by the concept they configure. Overview summarizes these pages and links to them instead of becoming another detailed view.
4. **Domain structure.** The panel uses the domain terms. Internal identifiers appear only in folded details, and names replace identifiers where they can be resolved.
5. **Honest state.** A count equals the length of the list it links to, and no state contradicts another fact.
6. **Quiet by default.** Healthy states take no extra space. Problems must be actionable; a one-off network error is not enough. Rows needing a person offer their action directly. Keep page explanations to one sentence and put further detail in the (?) tooltip. Destructive actions require confirmation.
7. **Consistent controls.** Use DeepSeek Harness design tokens and control behavior. The same information should look the same throughout the panel. Each settings block has one save bar, visible only while changes exist, a save runs or a save fails.
