## 对齐结论（需求级，冻结）

本需求分两部分：**对齐历史**与**对已对齐工单提问并把回答反馈到讨论列表**。本次 slice `C3` 只交付第二部分的**问答会话端口**（宿主侧能力），不涉及需求记录、HTTP API 与面板。

- 提问用 fork session 是冻结决定：从工单 worker 会话（`worker-<ticketId>`）最近一次已完成回合分叉出独立一次性会话，完整继承 worker 的上下文与工单目录，同时不碰工单状态。
- 备选已否决：把问题当 Ticket Input 投给工单（会 steer 正在跑的 worker、结束的工单还要 resume，问答混进工作状态）；新建空上下文会话（拿不到 worker 的推理与文件）。
- 回答来自从 `worker-<ticketId>` 分叉出的一次性问答会话：注册专门问答系统提示，只允许 `read / read_image / glob / grep` 只读工具，不写文件、不跑 bash、不启动 feature-exec；答完归档该会话。
- 工单从未启动会话时拒绝提问；无完成回合、fork 失败或超时 → 返回带原因的失败，由上层（C4）记录 `failed` 并可重试。
- 提问**不进 Engine**：不产生 Trigger/Eval/Ticket/Assignment，不唤醒、不 resume、不修改工单。
- C3 只提供可测试的端口；需求记录 `questions[]`、后台队列、重启重新排队、HTTP API 属 C4，面板入口与时间线属 C5。

## 现状与问题

- 工单 worker 会话的上下文（`worker-<ticketId>`）只能被 DSH 的 `sessionController.inspect` 读到，仓库里没有任何“fork 出一次性会话并向它提问”的端口。
- `src/app/sessions.ts` 目前只装饰两类会话：主 Session（`masterId`）与工单 worker Session（`ticketOfSession`）；其余 Agent 走 `limitSubagent`。fork 出来的会话既不是主 Session 也不是 worker 会话，若不显式装饰，会带着 worker preset 的全部工作工具（写文件、bash、feature-exec）跑问答。
- 仓库没有问答系统提示（`prompts/answer.md`），也没有会话归档的调用点（`workspaceRegistry.archiveSession` 尚未使用）。
- 测试夹具 `tests/fixtures/host.ts` 的 `sessionController` 只有 `create / selectModel / resolveAgent / rename / prompt / inspect`，没有 `fork`；`workspaceRegistry` 只有 `create`；会话事件固定为空、system prompt section 与 `tools.restrict` 的允许列表没有记录，无法断言“白名单恰为四个只读工具”“系统提示含问答指令”“会话被归档”。
