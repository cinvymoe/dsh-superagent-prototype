## 需求原文

> 当前的Issue都是以 PR 形式在远程仓库提交。最后执行，提交完成后。比如说我的插件是在本地运行的我需要本地的代码能够生效。所以说是否要在设置里面增加一个本地仓库的选项？或者讨论一下有没有什么更好的实现方式？能否在提示词或者流程里面新增加一个  本地合入并生效的流程。跟我讨论如何 方式实现。尽量满足高内聚低耦合。

## 对齐结论（需求级，冻结）

- 「本地合入并生效」拆成三步：**读运行检出的只读状态（本 slice C1）** → 合入动作（后续 slice）→ 重启生效（后续 slice）。
- 合入目标是「运行中的 dsh-superagent 加载的那份本地检出」：插件以 `dsh plugin --profile superagent add "link:$PWD"` 安装（`docs/006-deployment.md` 的 Install 段），升级也是在同一份检出里 `git pull && pnpm install && pnpm build` 再重启（Upgrade 段）。因此 C1 用 `packageRoot()` 定位它，**不引入新的配置键**，避免为只读状态扩大设置面。
- C1 只读：不落库、不改检出、不访问网络；合入与重启留给后续 slice 的路由。

## 现状与问题

- 管理 API 没有任何路由能读到运行检出的仓库名、路径、分支、HEAD 与脏树状态，面板（后续 slice）与合入动作都无从判断「现在能不能合入」。
- 升级流程 `git pull` 之后，磁盘 HEAD 与进程启动时的 HEAD 可能不同，而运行的仍是旧代码；没有 `restartRequired` 就无法区分「已合入」与「已生效」。
- 非 git 目录（如 `node_modules` 里的安装副本）、detached HEAD、非 main 分支、脏树都是「不能安全合入」的具体原因，需要稳定的原因码而不是自由文本。

## 验收标准（冻结版）

1. 临时 git 仓库上，https 与 ssh 两种 remote 形式（大小写不同、带/不带 `.git`）都能匹配出 owner/name；不匹配时 available=false 且给出 noRepository。
2. 非 git 目录、detached HEAD、非 main 分支、脏树分别返回对应原因码，同时仍返回可读到的路径/分支/HEAD。
3. restartRequired：磁盘 HEAD 与进程启动 HEAD 不同，或进程启动时是脏树 ⇒ true；两者一致且启动时干净 ⇒ false。
4. 该路由只执行本地只读 git 命令；测试断言没有 fetch/网络调用，且目标工作树未被修改。
5. 新模块与新测试在 007 的模块表、测试表登记；`pnpm check` 通过。

## 接口契约（供后续 slice 与面板消费）

- 路由：`GET deployment/checkout`，同一来源校验与其它路由一致；无需 setup 完成即可读。
- 响应（`CheckoutView`，JSON）：
  - `path`：检出根目录；不是 git 仓库时为被读的目录本身。
  - `repository`：origin remote 解析出的 `owner/name`（小写），无法解析为 `null`。
  - `branch`：当前分支；detached HEAD 为 `null`。
  - `head`：HEAD 提交，读不到为 `null`。
  - `dirty`：有任意已跟踪或未跟踪改动。
  - `available`：可安全接收本地合入（是 GitHub 仓库、在 main、干净）。
  - `reasons`：按 `CHECKOUT_REASONS` 顺序给出不可用原因；`available` 时为空。
  - `restartRequired`：磁盘 HEAD 与进程启动 HEAD 不同，或启动时是脏树。
- 原因码：`notGit`、`noRepository`、`detached`、`notMain`、`dirty`（`notGit` 时只给这一条，不再推 detach/notMain/dirty）。

## 避坑清单

知识库检索（关键词：`packageRoot`、`registerHttp`、`HttpHost`、`Api`、`CheckoutView`、`GIT_LOCATION`、`docs.spec`、`class-docs`；范围：`docs/`、`benchmarks/`、仓库设计文档）：

1. **`Api` 是路由类型契约**：只加 HTTP 路由不加 `src/app/api.ts` 条目会类型检查失败；`api.ts` 只能引类型，不能把 `checkout.ts` 的 Node 依赖带进面板 bundle（用 `import type`）。
2. **007 的模块表与测试表被 `tests/docs.spec.ts` 逐文件核对**：`src` 下每个 `.ts` 必须在 Modules 表，`tests` 下每个用例必须在 Tests 表，且表里不能出现不存在的路径。
3. **`class-docs.spec.ts` 要求每个 class 前有 JSDoc**：`Checkout` 类不能漏。
4. **起始快照语义**：快照必须在实例构造时就发起（不要等第一次 `status()`），否则「合入早于首次请求」会被误判为无需重启；快照失败（git 缺失）不能抛出，读不到就记 `head: null, dirty: false`。
5. **detached HEAD 的读法**：用 `git symbolic-ref --quiet --short HEAD`，失败即 detached；不要用 `rev-parse --abbrev-ref HEAD`（detached 时它返回字符串 `HEAD`，会被误当成分支名）。
6. **`notGit` 时不要再叠加原因**：没有仓库就没有「非 main / detached / 脏树」可言。
7. **测试别用本仓库自己的工作树**：一律 `mkdtemp` 建临时仓库，避免工作树本身脏/分支不同导致抖动；`git init` 显式 `-b main`，不依赖全局默认分支。
8. **只读性要可断言**：给 `Checkout` 注入记录型 git 执行器，断言子命令白名单 + 工作树哈希前后一致；不要把 `fetch`/`remote update` 之类写进读取路径。
9. **测试继承的 git 环境**：用 `tests/fixtures/git.ts` 的 `gitEnv()` 起子进程，避免外层 `git rebase --exec` 的 `GIT_DIR` 干扰。
