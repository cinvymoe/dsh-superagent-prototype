## 需求原文

> 当前的Issue都是以 PR 形式在远程仓库提交。最后执行，提交完成后。比如说我的插件是在本地运行的我需要本地的代码能够生效。所以说是否要在设置里面增加一个本地仓库的选项？或者讨论一下有没有什么更好的实现方式？能否在提示词或者流程里面新增加一个  本地合入并生效的流程。跟我讨论如何 方式实现。尽量满足高内聚低耦合。

## 对齐结论（需求级，冻结）

1. **不新增「本地仓库路径」设置**：运行中的检出由 `packageRoot()` 发现，合入目标由已有仓库链路的 code repository 决定。
2. **服务脚本是唯一写入者**：面板只经管理的 HTTP 路由调用 `scripts/dsh-superagent prepare --repository owner/name`；脚本负责 fetch → fast-forward → `pnpm install --frozen-lockfile` → `pnpm build`。
3. **「生效」的最后一公里显式交给部署**：合入构建后面板显示「重启后生效」；专用 profile 用 `restart`/`activate`，宿主 profile 由操作者重启宿主进程。插件不重启宿主。
4. **不改提示词/agent 团队文本**：合入与生效是部署/操作者动作，写进部署文档；可选的小时检查跑在另一个 profile。

本 slice 的范围：`docs/006-deployment.md` 的端到端流程、小时检查提示词与故障排查；`docs/005-panel.md` 的部署段落；`docs/007-architecture.md` 的 reload 说明；`tests/docs.spec.ts` 的文档断言。**不**改代码、脚本、面板、提示词或配置键。

## 事实契约（实现已合入，文档必须与之一致）

`scripts/dsh-superagent`（C2，`main` 已合入）：

| 动作 | 参数 | 退出码 | 关键输出 |
| --- | --- | --- | --- |
| `prepare` | `--repository owner/name`（必填；缺失或格式错 => 1） | 0 = 已最新或已合入并构建；1 = 拒绝/失败（拒绝时检出不变；构建失败回退旧提交并重建） | `prepare: up to date at <sha> on main`；`prepare: fast-forwarded from <sha> to <sha> on main`，随后 `$ pnpm install --frozen-lockfile`、`$ pnpm build` |
| `activate` | 同上，另可 `--if-idle`、`--only-when-behind`、`--respect-stop` | 0 = 已生效/跳过（已最新、空闲跳过、手动停止跳过）；1 = 拒绝、prepare 失败或回滚；2/3 = 启动健康检查给出的部件错误/等待 setup | `activate: backed up the database to <path>`、`activate: <sha> is running on main.`；跳过时 `activate: already up to date ...`、`activate: <n> Executor Session(s) are still working; activation is skipped.`、`Intentional stop is active; activation is skipped.`；回滚时 `activate: the new build did not start (...); rolling back to <sha>.` |
| `restart` | `--profile`、`--url`、`--respect-stop` | 0/1/2/3（与 `status` 同一套） | `dsh-superagent stopped.` |

部署页（C3，`main` 已合入）：`GET deployment/prepare` 给出 `checkout`（`path`、`branch`、`head`、`committedAt`、`dirty`、`remotes`、`restartRequired`）与 `chain`/`repository`/`available`/`reasons`/`running`；`POST deployment/prepare` 只跑 `prepare`，返回 `merged`/`head`/`log`，**从不重启或停止 dsh-superagent**；成功后页面显示「重启后生效」。`GET deployment/checkout` 仍可单独读到 `restartRequired`。

重启形态（对齐结论第 4 条）：

- **专用 profile**：`scripts/dsh-superagent restart --profile superagent`（或 `activate`，它合并 + 备份库 + 重启 + 健康校验 + 失败回滚）。
- **宿主 profile**（插件加载在他人监管的 DSH 实例里，例如本机 systemd 的 `dsh-web.service`，端口 8399）：插件不能重启宿主；由宿主监管者重启该进程。不得用 `restart`/`activate` 指向宿主 profile，那会把进程换成脚本的 tmux 会话。

## 避坑清单

1. **docs.spec 的链接规则**：编号文档只能链接更早的编号文档；`005` 不能链接 `006`。交叉引用写成 `006 → 005` 和 `007 → 006`，`005` 只做自述。
2. **docs.spec 的 `prose()` 折叠空白**：断言用连续整句、避免跨段；句子改动时同步改测试。
3. **SHA 占位**：文档里用 `<old sha>`/`<new sha>`/`<sha>`，与脚本输出前缀（12 位）一致；不要写不存在的命令参数（`prepare` 无 `--if-idle`）。
4. **两种形态的措辞**：专用 profile 由脚本管理（tmux `dsh-<profile>`）；宿主 profile 由外部监管者管理（本机 systemd `dsh-web.service`）。不得把 `restart`/`activate` 说成对宿主可用。
5. **「不重启」的边界**：面板路由与 `prepare` 不重启；`activate` 会重启它管理的专用 profile。两者要写清，别互相覆盖。
6. **小时检查的报告规则**：`activate` 的跳过与成功都退出 0，因此报告依据是输出行而不是退出码；提示词必须点名 `activate: <sha> is running on main.` 与回滚/失败行。
7. **`manually_stopped` / `--respect-stop`**：`activate --respect-stop` 在手动停止时退出 0；提示词不得把它当成失败汇报。
8. **文档测试只校验编号文档与 README/SETUP 的链接**：新增小节标题不得破坏既有 `## ` 结构；`006` 仍是 006（不新增编号文档）。
9. **不碰实现**：本 slice 不改 `src/`、`scripts/`、`prompts/`；若发现文档与实现不符，改文档而不是改代码。
10. **中英一致**：文档是英文；面板文案引用用页面上的英文标签（**Pull and build**、**Running checkout**、**Takes effect after a restart**）。
