C1 已删除 GitHub Source 的旧版单链路回退，`chains` 成为唯一配置。本 slice 承接第 1 点：**每个本地项目拥有并隔离自己的仓库链路**，创建/修改项目只影响该项目的链路，项目工单按自己的链路执行。

## 现状与问题

- `LocalProject` 只有单一 `repository`；`Runtime.ticketDeployment` 用项目的 `repository` 覆盖部署的 code/intake 仓库，项目与 GitHub Source 的 `chains` 没有任何关联。
- 面板创建项目只写项目记录，不写 `settings.sources.github.config.chains`，所以「每个项目独立」无法体现在 Source 的链路配置上：修改一个项目的仓库不会影响 Source 链路，但项目也不拥有链路，执行时仅靠运行时覆盖。
- 已有项目（只有 `repository`）需要在升级后绑定到 code repository 相同的既有链路，否则无法判断它属于哪条链路。

## 冻结验收标准（来自 assignment）

- POST local/projects 传入 name、intakeRepository、codeRepository、可选 worktreeRoot 后，settings.sources.github.config.chains 只新增一条 id=项目 id 的链路，所有已有链路行逐字段不变；返回的项目视图包含两条仓库。
- 仓库不可读/不可推送、名称重复、仓库格式非法时返回 400，且设置与项目记录都不留下失败产物。
- PUT local/projects/:id 只更新该项目自身的链路与元数据；另一个项目的链路行在更新前后深度相等。
- 项目工单的 execution.chain 等于项目链路的 id，DSH_SUPERAGENT_GITHUB_REPOSITORY 与 DSH_SUPERAGENT_GITHUB_INTAKE_REPOSITORY 等于该链路的 code/intake 仓库。
- 已有只有 repository 的项目在启动时能幂等绑定到 code repository 相同的既有链路；无匹配的项目仍按原 repository 执行，且不改动其他链路。
- pnpm check 全绿；docs/005 与 docs/007 描述项目拥有链路、旧记录回退与启动绑定。

## 任务拆解

- **T1（本 slice，唯一实现任务）**：项目模型与 API、项目链路协调层、运行时按项目链路执行、启动绑定、面板项目表单/展示、定向测试与文档更新。
  - 数据与 API：`LocalProject` 增加 `chain`/`intakeRepository`/`codeRepository`（`repository` 仅作为旧记录回退字段）；`POST local/projects` 接收两个仓库并原子地新增链；新增 `PUT local/projects/:id`。
  - 链路协调：新增项目链路协调层，负责把项目 id 作为 chain id 写入/更新 `settings.sources.github.config.chains`，复用 `Settings.save('source:github', …, 'panel')` 的部署探测（不可读/不可推送在写入前失败），保存项目记录失败时回滚链路。
  - 执行：`Runtime.ticketDeployment` 优先解析项目所属链路；项目工单的 `execution.chain`、`DSH_SUPERAGENT_GITHUB_REPOSITORY`、`DSH_SUPERAGENT_GITHUB_INTAKE_REPOSITORY` 来自该链路。
  - 启动绑定：`Runtime.initialize` 扫描只有 `repository` 的旧项目，按 code repository 匹配已有链路的 `codeRepository` 并写回 `chain`/两仓库，幂等；无匹配保持原样。
  - 面板：项目创建页收集接收 Issue 仓库与执行代码仓库；项目栏与需求详情展示两条仓库。
  - 测试：`tests/local.spec.ts`、`tests/local-align.spec.ts`、`tests/panel-*` 与 fixture 覆盖六条冻结标准；`pnpm check`。
- **不在本次**：其他 Source、旧版配置的数据库迁移（C1 已做读取归一化）、项目删除/链路删除。
