## 需求原文

> 需求列表 如果全部执行完毕 状态 新增待关闭

## 对齐结论（需求级，冻结）

需求：Discuss 的「需求列表」在一条需求的全部切片执行完毕时，新增「待关闭」状态，让 owner 看出这条需求只剩关闭动作。

语义决定（本次拍板）：

- 「全部执行完毕」= 需求的 alignment 已 confirmed、至少有 1 个切片、当前 alignment 的每个切片都能按 core 的稳定 ticket id 找到对应工单、且这些工单全部已有 `ended` 记录。
- 结束方式不区分：executor 的 ready（completed / merged / closed）、dropped 以及 owner 手动停止（stopped）都算执行完毕。「待关闭」只表示执行已停止、只剩关闭动作，不声称任务成功；这样 owner 停掉切片后需求不会永远停在「开放」。
- 零切片或任一切片缺工单（历史/异常数据）一律不算执行完毕，避免误报。

展示决定：新增的「待关闭」加在需求状态上（现有状态为「开放」「已关闭」），而不是替换对齐标签。用户说的是「状态」，执行完毕属于需求生命周期；对齐结果仍是「已确认」，所以完成行的两个标签读作 [待关闭][已确认]。需求关闭后状态显示「已关闭」；未对齐、待审阅、已打回、仍在执行的需求状态仍是「开放」。列表与详情页头共用同一个 stateTag，详情自动一致。

实现决定：状态不落库、无迁移、无状态机，读取时派生。新增共享视图类型 `LocalIssueView = LocalIssue & { slicesFinished: boolean }`，由 `LocalIssues.view()` 计算，所有返回 issue 的 local 路由统一返回该视图（列表、详情以及创建/评论/对齐/确认/关闭的返回体）；客户端只渲染，不重复工单 id 规则。把 `evals.acceptPlan` 里的 `key('ticket','plan',issueId,sliceId)` 提取为 core 导出函数 `planTicketId()`，派发与派生共用一处，避免 key 规则漂移。工单之后被人消息恢复为 open 时，派生值自动回到 false，状态回到「开放」，无需额外处理。

范围：不做自动关闭、不做进度 N/M 或耗时统计、不改工单结束规则/对齐语义/TicketOutcome 集合、不改其它页面或标签、不回填历史数据。

切片决定：只切一个 full 切片 C1。这是单一端到端机制，生产改动集中在约 9 个文件且每处很小；若拆成「服务端字段」+「前端标签」两片，会先合入无人使用的契约并为一个小改动引入串行依赖，收益低于成本。full 因为涉及 HTTP 契约与 UI，需要独立评审、测试和 Before/After 证据。

## 现状与问题

- `LocalIssue` 只有 `state: 'open' | 'closed'` 与 `alignment.status`，面板 `stateTag`（`src/client/discuss.tsx`）只按 state 显示「开放」「已关闭」；一条需求的全部切片工单结束后，列表与详情仍显示「开放」，owner 看不出只剩关闭动作。
- 需求详情已能列出关联工单，但列表行没有「执行已结束」的派生信号；服务端也没有任何接口暴露「切片是否全部结束」。
- 切片工单 id 目前只在 `src/core/evals.ts` 的 `acceptPlan` 里用 `key('ticket','plan',issueId,sliceId)` 现算，派生视图若复制这段规则会漂移。
- `LocalIssue` 是持久化记录（KV `local-issue:`），不能为展示状态加字段，否则需要迁移，也会让派生状态与工单真实状态不一致。

## 验收标准（冻结版）

1. 已确认对齐的需求只要还有切片工单未结束，`GET local/issues` 与 `GET local/issues/:id` 返回的 `slicesFinished` 为 false，列表行与详情页头的状态标签仍为「开放」。
2. 该需求每个切片工单都 ended 后，两个接口返回 `slicesFinished: true`，open 需求的列表行与详情页头状态显示「待关闭」/「Pending close」，对齐标签仍是「已确认」；executor 的 ready 结束与 owner 停止（stopped）两种方式都计入。
