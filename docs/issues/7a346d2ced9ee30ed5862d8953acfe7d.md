## 需求原文

> 当前的Issue都是以 PR 形式在远程仓库提交。最后执行，提交完成后。比如说我的插件是在本地运行的我需要本地的代码能够生效。所以说是否要在设置里面增加一个本地仓库的选项？或者讨论一下有没有什么更好的实现方式？能否在提示词或者流程里面新增加一个  本地合入并生效的流程。跟我讨论如何 方式实现。尽量满足高内聚低耦合。

## 对齐结论（需求级，冻结）

1. **不新增“本地仓库路径”设置**：运行中的检出由 `packageRoot()` 发现，代码仓库由已有 chain 匹配；设置页只读展示。
2. **部署层新增“本地检出”能力**：只读观察（C1）+ 合入构建（C2 的脚本动作，C3 的面板动作）。
3. **服务脚本是唯一写入者**：`prepare` 只合入并构建；`activate` = prepare + 优雅停止 + SQLite 备份 + 启动 + 健康校验，失败自动回滚。
4. **“生效”的最后一公里显式交给部署**：专用 profile 用 `restart`/`activate`；宿主 profile 由操作者重启宿主进程。
5. **不改提示词/agent 流程文本**；流程写进部署文档（C4）。

本 slice 的边界：`scripts/dsh-superagent` 的 `prepare`/`activate` 两个动作、`tests/service-script.spec.ts` 的真实临时 git 检出 + bare 远端测试、`docs/006-deployment.md` 与 `docs/007-architecture.md` 的相应段落。**不**改面板/API、不新增配置键、不重启脚本不管理的宿主。

## 现状与问题

- `scripts/dsh-superagent` 现有动作只有 `start`/`stop`/`restart`/`status`；升级仍靠人手工 `git pull && pnpm install && pnpm build` 再 `restart`，且没有任何安全边界（脏树会拉不动、分叉会产生 merge commit、构建失败会把检出留在“已合入但未构建”的半状态）。
- `restart` 会结束正在执行的 Assignment，且升级后的库由新版本迁移后，旧版本无法打开——所以“合入并重启”必须先备份 `<stateDir>/orchestrator.sqlite`。
- `GET state` 已经返回 `setup.machine.stateDir` 与 `load.running`，脚本可以用它定位数据库、判断是否空闲，不需要新增接口或配置。

## 验收标准（冻结版）

1. 临时真实 git 检出 + bare 远端领先时：prepare 只做 fast-forward 到新提交，桩 pnpm install/build 执行，不产生 merge commit，输出含 from/to；再次执行报告 up-to-date，不重启、不重复构建。
2. 脏树、分叉、detached、非 main、`--repository` 与检出 remote 不匹配 => 退出 1 且检出与服务均未变；并发第二个 prepare 被拒绝。
3. activate：从 `GET state` 读到 stateDir，停止后生成 orchestrator.sqlite 备份，启动并通过健康校验；`--if-idle` 在有执行中 Assignment 时跳过；`--respect-stop` 在手动停止时跳过；`--only-when-behind` 在已最新时跳过。
4. 注入启动失败：恢复到 prepare 前提交与备份库，重新安装/构建，旧版本启动成功并打印回滚，退出 1。
5. 现有 `tests/service-script.spec.ts` 全部通过；`pnpm check` 通过。

### T1 acceptance

- `prepare --repository <owner/name>`：远端匹配（`git remote -v` 的 URL 末两段，大小写与 `.git` 后缀不敏感）→ 分支必须是 `main` 且工作树干净 → `git fetch --no-tags <remote> +refs/heads/main:refs/dsh-superagent/main` → 仅 fast-forward（`merge --ff-only`）→ `pnpm install --frozen-lockfile` + `pnpm build`。移动时输出 `prepare: fast-forwarded from <sha> to <sha> on main`；未移动时 `prepare: up to date at <sha> on main` 且不构建。安装/构建失败则 `reset --hard` 回原提交并重建，退出 1。
- `activate --repository <owner/name>`：`--respect-stop` 且存在 `manually-stopped` 标记 => 跳过（0）；否则 `GET state` 取 `setup.machine.stateDir` 与 `load.running`，服务不应答即拒绝（1）；`--if-idle` 且 `load.running > 0` => 跳过（0）；`prepare` 后 `--only-when-behind` 且提交未移动 => 跳过（0）；否则 `stop`（非手动）→ 备份 `<stateDir>/orchestrator.sqlite`（含 `-wal`，落在 `.artifacts/backups/orchestrator-<profile>-<stamp>/`，保留 10 份）→ `start` 并等健康。启动失败则停掉新版本、`reset --hard` 回 prepare 前提交、恢复备份库、重装重建、启动旧版本、打印回滚、退出 1。
- 并发：两个动作沿用 profile 的 `operation.lock`，第二个并发调用退出 1。
- `tests/service-script.spec.ts` 覆盖：FF + 不重建 + 幂等、脏树/分叉/detached/非 main/仓库不匹配/并发拒绝且 HEAD 不变、activate 备份与重启、三个跳过开关、启动失败回滚（提交、库、构建、旧版本存活）。
- `pnpm vitest run tests/service-script.spec.ts`、`pnpm check` 通过；`git diff --check` 无输出。

## 避坑清单

知识库检索（关键词：`scripts/dsh-superagent`、`prepare`、`activate`、`orchestrator.sqlite`、`stateDir`、`manually-stopped`、`operation.lock`；范围：`benchmarks/`、`docs/issues/`、`docs/006-deployment.md`）：

1. **`.artifacts` 必须在检出的 `.gitignore` 里**：`main()` 在任何动作之前就建 `control/<profile>`，否则 prepare 的脏树检查会把自己刚建的目录当成改动。真实仓库已忽略 `.artifacts/`。
2. **`--respect-stop` 必须在读 `GET state` 之前**：手动停止的服务本来就不应答，先读 state 会把“跳过”变成“拒绝”。
3. **不要用 `git pull`**：它的 `branch.<name>.remote` 可能指向 upstream（本机 web 检出即如此），且分叉时会产生 merge commit。必须按 `--repository` 匹配 remote 后 fetch 到 `refs/dsh-superagent/main`，再 `merge --ff-only`。
4. **备份要在 `stop` 之后**：服务运行中 SQLite 处于 WAL 模式，热拷贝可能拿到不一致的快照；优雅停止会 checkpoint。
5. **`start` 失败会留下进程**：`start` 超时只说“Any running process was left intact”，回滚前必须先 `stop`，否则第二个实例会被拒绝启动。
6. **测试里的 git 用户身份**：全局 `user.useconfigonly=true`，测试必须显式 `-c user.name=… -c user.email=…` 提交；bare 远端放在检出的 `remotes/<owner>/<name>.git`（被忽略），`--repository` 才能按 URL 末两段匹配上。
7. **回滚测试要能区分两版构建**：健康检查的模拟服务按“当前存活 pid”应答，第一次启动故意不给 pane PID（新版本不健康），回滚构建后的第二次启动才给存活 PID，从而证明“旧版本启动成功”。
