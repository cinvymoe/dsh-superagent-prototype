## 对齐结论（需求级，冻结）

- 对齐结果保留**轮次历史**：每次 Aligner 重新提案生成新的一轮，旧的未决轮次标记 `superseded`；人打回的轮次保留 `rejected` 与打回原因。
- 打回某一轮时，把打回原因作为该需求 Thread 上的一条 **human 本地触发** 落库，使 Aligner 会话能收到反馈并再次 `orchestrator_align`。
- 人的决定只作用于**当前（最新）轮**：带旧 `roundId` 的决定经 HTTP 被拒绝并给出明确错误码。
- **最新轮已确认后**不再接受新的对齐提案（`orchestrator_align` 返回明确错误，轮数不增加）。
- 派发只取**最新轮（已确认）**的切片。
- 存量记录只有单个 `alignment` 字段时，读取时按**一轮历史**归一化，不批量迁移。

## 验收标准（冻结版）

1. `tests/local.spec.ts`：连续两次 `propose` 得到两轮且旧 `proposed` 为 `superseded`；`decide('reject','缩小范围')` 后该轮 `rejected` 且 `reason` 正确，同时新增一条 human 本地触发、文本含打回原因；此后 `propose` 追加第三轮；直接写入带旧 `alignment` 字段的记录能读出一轮历史。
2. `tests/local-align.spec.ts`：打回后 Aligner 会话收到该反馈并再次 `orchestrator_align` 成功；确认只派发最新轮的切片；带旧 `roundId` 的决定经 HTTP 返回拒绝且带明确 code；最新轮已确认后再 `orchestrator_align` 返回明确错误且轮数不增加。
3. `tests/locales.spec.ts` 通过（新错误码有中英双语条目），`pnpm typecheck` 与上述两个测试文件通过。

## 现状与问题

- `LocalIssue.alignment?: LocalAlignment` 只有一个槽位：Aligner 再次 `propose` 会覆盖上一轮，讨论页看不到历史，打回原因只留在被覆盖的轮次里。
- `LocalAlignment` 没有轮次标识，人的决定无法表达“针对哪一轮”，旧页面上的决定可能误确认新轮。
- `decide('reject', reason)` 只写回记录，不产生任何人类触发，Aligner 会话不会收到打回反馈，需要人工再评论才会重新对齐。
- `propose` 在最新轮已确认后仍会覆盖记录，允许绕过“确认即冻结”的语义。
- 派发路径（`planInput` / `dispatchPlan`）读取单槽位，轮次化后必须显式取最新轮。

### T1 acceptance

- `LocalAlignment` 增加 `roundId`，状态集合增加 `superseded`；`LocalIssue` 增加 `alignments?: LocalAlignment[]` 轮次历史（最新轮在末尾），保留 `alignment` 作为最新轮的读取镜像，存量只有 `alignment` 的记录读取时归一化为一轮。
- `propose` 追加新一轮：旧的 `proposed` 轮次变 `superseded`；最新轮已 `confirmed` 时抛 `UserError('alignmentConfirmed')` 且不写记录。
- `decide` 支持可选 `roundId`：与最新轮不一致且该轮存在时抛 `UserError('alignmentRoundStale')`；`confirm` 更新最新轮为 `confirmed`、无切片抛 `planEmpty`；`reject` 写 `rejected` + `reason`，并向需求 Thread 落一条 human 本地触发，文本包含打回原因（无原因时给出可读的默认反馈）。
- `planInput` / `dispatchPlan` / `orchestrator_align` 工具一律读取最新轮；确认只派发最新轮切片。
- HTTP `POST local/issues/:id/alignment/decision` 接受可选 `roundId` 并透传到 `decide`；`src/app/api.ts` 同步类型；`UserError` 经既有 `failure()` 映射为 400 + `code`。

- 面板决定携带当前轮 `roundId`，并认识 `superseded` 状态（若改动面板，则同步 `tests/fixtures/panel-server.ts` 与 `tests/panel-discuss.spec.tsx`）。

## 避坑清单

知识库检索（关键词：`LocalIssue`、`alignment`、`orchestrator_align`、`USER_ERRORS`、`userError.`、`local/issues/*/alignment`；范围：`benchmarks/`、`docs/issues/`、仓库设计文档）：

1. **新错误码必须同时有 zh/en `userError.*` 文案**，否则 `tests/locales.spec.ts` 失败；`tests/local.spec.ts` 已有用 `(error as { code?: unknown }).code` 断言的先例。
2. **旧记录兼容**：`LocalIssue` 缺 `alignments` 必须合法，读取时归一化，不得在启动迁移里批量补写；`alignment` 镜像不能与历史脱节（写入时以 `alignments` 为唯一真相）。
3. **反馈触发与 `comment()` 同形**：用 `localTrigger({ issue, text, at, id })` + `host.receive(...)`；触发必须是 `human: true`，文本含 `reason`，且同一轮重复 `reject` 不得重复生成触发。
4. **确认幂等**：重复 `confirm` 仍返回 200，`dispatchPlan` 复用既有 Ticket（`Engine.acceptPlan` 已保证），不得新增 Ticket。
5. **决定顺序**：先校验轮次与状态再写记录；旧 `roundId` 的拒绝发生在写记录与派发之前，记录保持不变。
6. **面板/夹具联动**：`alignment` 类型若收紧（`roundId` 必填），`tests/fixtures/panel-server.ts` 与 `tests/panel-discuss.spec.tsx` 的构造数据要同步，否则 `pnpm typecheck` 失败。
7. **`docs/007-architecture.md` 的模块/测试表**：本 slice 不新增 `src`/`tests` 文件时无需改；若新增测试文件必须登记，`tests/docs.spec.ts` 会校验。
8. **不要改派发后只读的判据**：执行模式只读仍以“存在 `plan.issueId === issue.id` 的 Ticket”为判据，本 slice 不触碰。
