## Outcome

A host-side, testable one-shot Q&A port for a Ticket: `Questions.ask(ticket, question, { timeoutMs?, signal? })` forks
`worker-<ticketId>` at its latest completed turn, decorates the fork with the answer prompt and exactly
`read`/`read_image`/`glob`/`grep`, delivers the question, reads the assistant text the fork produced after its inherited
prefix, and archives the fork. Asking writes nothing: no Trigger, Eval, Ticket or Assignment, no resume or wake, no
`store.tickets` write. Failures return `{ ok: false, reason, message }` for `no-session`, `no-completed-turn`,
`fork-failed`, `timeout` and `empty-answer`, and every path that created a fork archives it again.

The requirement record (`LocalIssue.questions[]`), the HTTP API and the restart queue are C4; the panel entry and
timeline are C5.

## Context

The alignment decided to answer a Ticket question through a fork of its worker Session rather than as a Ticket Input
(which would steer a running worker or resume an ended one) or a fresh empty Session (which would lose the worker's
context and files). C3 delivers the port only, so C4 can persist and serve questions without duplicating session logic.

## Risks and limitations

- The live DSH path (real fork/cancel/archive/permissions and answer quality) is unit-tested only against the in-memory
  host fixture; the requirement's overall acceptance asks for one manual live verification after deployment, which this
  slice does not pretend to cover.
- `QuestionsHost.store` is part of the host shape for C4 but is not read by the port (by design: asking must not touch
  the Ticket).
- `Questions` is not constructed by `Runtime` yet; C4 wires it to the requirement record and `POST
  local/issues/:id/questions`, C5 to the panel.
