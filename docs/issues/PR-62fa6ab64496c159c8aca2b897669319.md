## Outcome

A requirement can be asked about one of its dispatched Tickets. `POST local/issues/:id/questions` records `asked` on the
requirement record and returns at once; the background queue answers through the C3 `Questions` port (a Session forked off the
Ticket's worker) and writes `answered` with the answer, or `failed` with the reason. `POST
local/issues/:id/questions/:questionId/retry` re-queues a failed question under the same record. A start re-queues every
question a previous run left `asked`, and stopping writes nothing so the next start retries it. Asking never reaches the
Engine: no Trigger, Eval, Ticket or Assignment is written and the Ticket is only read.

## Context

C3 delivered the fork-based Q\&A port; C4 persists and serves questions on the requirement record so the panel (C5) can ask
without duplicating session logic. The alternative — delivering the question as a Ticket Input — was rejected because it would
steer a running worker or resume an ended one, and a fresh empty Session would lose the worker's context.

## Risks and limitations

- A question about a Ticket whose worker Session is no longer open fails with the port's `no-session` reason and can be
  retried once the Ticket runs again; the record keeps the reason.
- The panel has no ask entry yet (C5); this PR adds the records and the typed API only.
- Live fork answering on a deployed instance remains the manual verification C3 recorded; the tests here cover the
  composition with a simulated fork turn and the port's own behaviour with C3's tests.
