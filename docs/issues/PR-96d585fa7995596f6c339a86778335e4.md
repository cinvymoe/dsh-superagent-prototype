## Outcome

需求详情的「关联工单」每一行在「打开 Session」旁提供「提问」：内联输入框只就这一张工单提问，提交后 `POST local/issues/:id/questions`（body `{ ticket, text }`），随后经页面既有的 `act()` 重读需求，问题按 `askedAt` 进入消息记录的时间线（newest-first，与真人消息、智能体回复同列）。每条问题标注所属工单与时间，并按状态呈现：等待回答… / 已回答（回答在独立「回答」块按 Markdown 渲染）/ 回答失败（原因 + 「重试提问」，重试发 `POST local/issues/:id/questions/:questionId/retry` 并把同一记录改回等待）。问题不写入线程 Trigger 时间线，因此需求原文、问题与回答在页面上各出现一次。

## Risks and limitations

- **Stacked PR**：#37（C4）必须先合并；在那之前本 PR 的 diff 含 C4 的提交，视觉 Before 取 C4 合入后的基线而不是 deployment `main`。
- **字段命名**：冻结判据写「body 含 ticketId」，C4 冻结契约的字段是 `ticket`；面板按宿主契约发 `{ ticket, text }`（否则真实宿主 400），测试断言的是后者。
- **等待态不在截图里**：seeded 的 `asked` 记录会在宿主启动时被 `resume()` 重新处理并落 `failed`（demo state 没有真实 worker 会话），因此截图呈现 `answered` 与 `failed`；`asked` 的渲染由面板用例覆盖。
- **提问长度**：客户端 `maxLength` 4000 与宿主 `QUESTION_CHARS` 同值但无法共享常量（面板不 import `src/app` 运行时），以注释与文档记录。
- **环境相关既有失败**：未 `env -u GIT_CONFIG_GLOBAL` 时 `tests/runtime.spec.ts` 两个用例失败；未设 `LC_ALL=C` 时 `tests/environment.spec.ts` 因本机中文 git 输出失败。二者与本切片无关，`pnpm check` 证据在干净环境产生。
